## Original issue body

## Problem

In a live meeting, the warning chime (and sometimes the timeout chime) played out of sync for one participant, heard by others as an echo. Evidence gathered:

- Everyone hears the **start** chime together, but the **warning** and **timeout** chimes drift.
- One participant was consistently offset. The gap was about 1.5 minutes, close to the **default** warning point (total 15:00, warn at 12:00), suggesting a client running the old default config while the moderator's client ran a changed value.
- With all but the active speaker muted, the moderator saw the active speaker's mic mute for the chime, then a second mute a few seconds later, and could not tell if the second was their own local chime.

## Root cause

The server is authoritative for elapsed time and config, but it only pushes SSE state on a **control action** (start, pause, set, and so on) and once on connect. There is **no periodic re-sync**. Between actions each client free-runs on its own clock and decides locally when to chime. So any client that misses a broadcast, is throttled, or is suspended keeps a **stale clock and stale config** until the next control press, which may never come within a run. That single gap explains all three symptoms: the seconds-level echo, the minute-and-a-half straggler, and the default-warning chime firing alongside the changed one.

A related client defect: `muteForCue` starts the audio immediately but mutes the mic only after an async `isAudioMuted()`/`toggleAudio` round trip, so the opening sliver of every cue can leak. Its restore also toggles audio back on unconditionally, which can fight the operator's all-but-active-speaker muting.

## Fix (three parts)

1. **Server-fired time-based cues.** A hub ticker emits an explicit cue signal (`warning`, `end`, `grace-end`) on the SSE stream at the instant elapsed passes each threshold, once per run (elapsed-boundary highwater, carrying a stable cue id). Clients play those cues on receipt, not on a local threshold crossing. Start/pause/resume cues stay client-side on state deltas, since they already ride the control broadcast and are in sync.
2. **Heartbeat re-anchor.** The same ticker re-broadcasts current authoritative state every ~10 s of server time, so a stale, reconnected, throttled, or suspended client is pulled back to the correct elapsed and config well before any cue. Doubles as SSE keepalive.
3. **Mute tidy-up (client).** Mute the mic before starting the cue, pad the mute a few hundred ms either side, and restore only once and only when safe, so the cue neither leaks nor fights operator muting.

The visual countdown stays local and smooth between events, re-synced by the heartbeat.

## Process

Emergency fix authorized under BYPASS-GATE-7. Server behaviour (cue timing, fire-once, heartbeat) covered by regression tests over the SSE stream with the injected clock. The client audio and mute behaviour is operator-verified (UT), since there is no JS test harness in this repo.

## Test plan

- RT: warning cue emitted over SSE when elapsed reaches warnAt, exactly once, with a cue id.
- RT: end cue emitted at total; grace-end cue emitted at total+grace, and suppressed when extended.
- RT: heartbeat state delivered without any control action after the interval, re-anchoring elapsed.
- RT: a cue is not repeated on later ticks or heartbeats (fire-once).
- RT: a late subscriber after a cue has fired receives no cue on its initial state.
- UT: in a live meeting, the warning and timeout chimes play together for all participants, no echo, and the active speaker's mic is not left unmuted afterwards.

### Comment by tigger-developer at 2026-08-21T00:05:37Z

Implemented under BYPASS-GATE-7 in `ec41e0b`.

**Server** (`internal/server/timer.go`)
- Hub ticker (runs only while a subscriber is connected) emits `warning` / `end` / `grace-end` at the instant elapsed passes each threshold, once per run (elapsed-boundary highwater), each with a stable cue id.
- Re-broadcasts current state every ~10s to re-anchor stale/reconnected/suspended clients; doubles as SSE keepalive.
- A first subscriber joining mid-run seeds the highwater from current elapsed, so a late joiner gets no stale cue.
- Ticker broadcasts run under the hub lock (non-blocking sends) so a concurrent Unsubscribe cannot close a channel mid-send.

**Client** (`internal/server/static/timer.js`)
- Time-based cues play on the server's instruction (deduped by cue id), not the local clock; start/pause/resume stay local on state deltas.
- Mic muted before the sound with padding either side; restore only when this client muted and the operator has not since changed the mic.
