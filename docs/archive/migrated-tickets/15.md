## Original issue body

## Problem

Writers' groups run timed turns: each participant gets a fixed number of minutes to read or speak. The group previously relied on Zoom's on-screen timer with an end chime. 8x8 JaaS has no moderator-controlled countdown with an alert (only cumulative speaker stats and an elapsed-time display), so the meeting page needs its own.

The feature is a single shared timer per room, authoritative on the server and pushed to every participant, controlled by any moderator, with an on-screen countdown, phase colours on the banner, and audible cues. Different rooms hold independent timers; within a room, all moderators and participants see and hear the same timer.

### Behaviour summary

- Any moderator can configure and control the room's one timer; all moderators see identical controls; all participants see the countdown and hear the cues.
- Three settings: **total time** (mm:ss), **early-warning** (percent of total), **grace** (percent of total, counts up after the total elapses).
- Phases and banner colours for everyone: no timer = blue; running before the early-warning = green; after the early-warning = amber; past the total, within grace (counting up) = red; past the grace limit = black, alternating black/red about once per second for ten seconds, then auto-reset to blue.
- Sounds for everyone: a start chime when the timer starts, a pause chime when it is paused, a resume chime when it resumes, an early-warning ding entering the amber phase, an end chime at the total, an end-of-grace chime when the grace limit passes. Audio files are supplied by the operator.
- While any chime plays, each participant's own microphone is briefly muted so the chime is not captured and re-broadcast into the meeting, then restored to its prior state. This applies to all six cues; it may briefly clip an active speaker (for example at the early-warning ding), which is accepted because the cue is meant to interrupt and must be heard by everyone.
- Grace counts up automatically the moment the total elapses, so a busy moderator need do nothing. `Extend` lets the count-up continue past the grace limit; `Stop` returns the timer to its reset state.
- Moderator controls by phase: stopped = `Set`, `Start`; running = `Pause`; paused = `Resume`, `Reset`, `Restart`; grace = `Extend`, `Stop`. Non-moderators see no controls and see numerals only while a timer is active.

### Defaults and open interpretations (carried from design discussion)

- Default settings: total 15:00, early-warning 20%, grace 30% (the values in the operator's worked example; the earlier 10%/20% prose is superseded by these).
- Early-warning is the final stretch: a 20% warning on a 15:00 timer turns the banner amber at 12:00 (3:00 remaining).
- `Extend` lets the count-up proceed past the configured grace limit until `Stop`; without it, reaching the grace limit ends the timer.

## Solution Design

### Recommended approach

Implement a server-authoritative per-room timer with a Server-Sent Events (SSE) stream to participants and authenticated control endpoints for moderators, plus a thin client renderer in the existing banner. All timer arithmetic (thresholds, phase, remaining, count-up) lives on the server so it is single-sourced, testable through the HTTP boundary, and identical for every participant; the client only renders state and plays audio.

**State.** A `TimerHub` in `internal/server` holds `map[string]*roomTimer` guarded by a `sync.Mutex`, plus per-room subscriber channels. `roomTimer` stores the configuration and lifecycle anchors (start instant, accumulated pause, paused flag, extended flag). Phase, remaining, and count-up are pure functions of the configuration and `s.now()`, so tests drive them with the injected clock (`Config.Now`, already present).

Two persistence tiers. The **configuration** persists to a new last-row-wins CSV log, `TimerSettingsLog` over `timer_settings.csv` in the state directory, keyed by room, following the same append-only mutex-protected read-all pattern as `RoomsLog` (and tested the same way as AC7.7's restart RTs, by reconstructing the server against the same state directory). The **live running state** (running, paused, elapsed) stays only in memory and is cleared by a server restart.

Kept separate from `rooms.csv`, rather than folded in, because that log is read as latest-row-per-room-wins over a whole-row snapshot. Timer configuration changes independently of the created/cancelled lifecycle, so sharing one table would force either full-row rewrites (a timer change restating the current window and status, inviting staleness and races) or per-field last-write merging, and would reopen #7's tested schema. A separate log keeps each store's "latest row is current" invariant simple.

**Client reconnect.** Because the server is authoritative and holds the live timer in memory, a participant or moderator whose browser reloads or re-authenticates mid-session opens a fresh subscription and immediately receives the current in-progress state (AC15.7); the countdown is uninterrupted for everyone else, and the moderator regains controls once the token is present again. This is distinct from a server restart, which is the only event that clears the in-memory runtime (see Limitations).

**Routes** (parsed in `handleRoom` alongside the existing `moderatorRoute` handling, before the single-segment slash rejection):
- `GET /<room>/timer` returns the current state as JSON (initial render and test oracle).
- `GET /<room>/timer/events` is the SSE stream: it emits the current state on connect and a new state event on every change.
- `POST /<room>/timer` applies a control action (`{ "action": "...", "config": {...} }`), authenticated as a moderator for that room and returning the resulting state.

**Auth.** Control requests reuse the existing moderator-token verification (`hasValidModeratorJWT` / `verifyModeratorPayload`), scoped to the path room or a `*` wildcard, exactly as the room gate and Record button already work. The read stream is available to whoever can load the room page (the page itself is already gated by #7).

**Live transitions.** Time-based transitions with no control action (entering amber, reaching the total, reaching the grace limit, ending the flash window) are pushed to subscribers via `time.AfterFunc` scheduled on start/resume and rescheduled on pause/extend. Clients also self-tick from the anchors in the last state event, so the countdown advances smoothly between server events and a missed push still corrects on the next event.

**Client.** The banner script (currently the Record button and tile-view logic) gains: an `EventSource` subscription to `/<room>/timer/events`; rendering of the numerals (Iosevka, bold) and phase colour; the moderator control set, shown only when a moderator token is present (same gate as the Record button); a configuration popover anchored under `Set`; and six `<audio>` elements (start, pause, resume, warning, end, end-of-grace) armed on the existing join gesture so a cue is not blocked by autoplay policy. Controls issue `fetch` POSTs to the control endpoint.

**Chime input mute.** When any chime plays, the client reads the local mute state via `JitsiMeetExternalAPI.isAudioMuted()`; if the microphone is unmuted it mutes it (`executeCommand('toggleAudio')`) and restores it on the chime element's `ended` event; if already muted it leaves it muted. This suppresses each participant's own chime from being captured and re-broadcast. It applies to all six cues; the operator has accepted that this briefly clips an active speaker (notably at the early-warning ding), because the cue is meant to interrupt and must be heard by everyone. The exact mute command and whether an explicit set-mute exists (versus toggle-and-restore), and the reliability of muting and restoring within a sub-second chime, must be confirmed in the implementation spike.

**Assets.** The Iosevka faces and the six operator-supplied audio files are embedded and served through the existing `//go:embed static` mechanism. The Iosevka standard-width faces are staged at `internal/server/static/fonts/` (Regular, Bold, Italic, BoldItalic, Heavy, HeavyItalic; the Extended and UltraExtended width variants are excluded); the timer numerals use Bold. The audio files are staged at `internal/server/static/sounds/`: `timer-start.m4a` (start), `pause.m4a` (pause), `un-pause.m4a` (resume), `early-warning.mp3` (warning), `timer-end.mp3` (end), `grace-end-period.mp3` (end-of-grace). Formats are mixed MP3 and M4A/AAC; both are broadly supported by current browsers, to be confirmed in the spike. Because `//go:embed all:static` covers this directory, the files are embedded on the next build and served under `/static/sounds/` by the existing static handler; wiring and commit occur under this issue's implementation.

### Decomposition

This is large enough to implement as two sequenced pieces under this design: (1) the server timer core (hub, routes, auth, state machine) covering AC15.1 through AC15.9 (all RT); (2) the client banner UI and audio covering AC15.10 through AC15.14 (all UT). They can be separate sub-issues or two commits within this one; the AC table is the shared spec either way.

### Patterns to follow

- Go server, SSE, and control endpoints on stdlib `net/http`; `encoding/json` for state; `html/template` for any server-rendered markup (GO.md "Standard Library Preference"; no third-party SSE or websocket dependency).
- Injected clock via `Config.Now` for deterministic phase tests, matching the existing gate and registry tests.
- Mutex-guarded shared state with a clear goroutine lifecycle for `AfterFunc` and subscriber channels; run `go test -race` (GO.md "Concurrency").
- Client JS as ES modules, `const`/`let`, strict equality, `async`/`await`, promise rejections handled (WEB.md "JavaScript"); `rem` units, mobile-first, semantic markup, WCAG AA contrast for the banner states (WEB.md "CSS", "HTML").
- Reuse `parseDomain`, the banner styling, and the moderator-token gate already used by the Record button.

### Anti-patterns to avoid

- No per-second server push to every subscriber; push state changes only and let the client tick locally (CODING.md "Prohibited Anti-Patterns", `sleep`/poll and needless load).
- No embedding one language as a string inside another: server-rendered markup uses `html/template`, not string concatenation (CODING.md "Code Structure").
- No silent error suppression on the control or stream paths; a failed action returns a diagnostic, not a swallowed error (CODING.md "Error Suppression"; GO.md "Error Handling").
- No new browser test stack introduced without explicit approval; client behaviour is verified by UT (WEB.md "Build and Test Tooling", TESTING.md "Test architecture changes").
- Tests must not grep source; server behaviour is exercised through the HTTP endpoints (TESTING.md "The real-user test").

### Test plan and locations

- `tests/regression/timer_test.go`: RT-15.1 through RT-15.36. Server behaviour through the HTTP boundary using `httptest` and an injected clock. The persistence RTs (RT-15.33 to RT-15.36) reconstruct the server against the same state directory to simulate a restart, mirroring the room-registry restart tests. Phase and computation RTs read `GET /<room>/timer`; control RTs POST and read the returned state; subscription RTs (RT-15.26 to RT-15.30) open the SSE stream and read events; concurrency RTs use `go test -race`. The real-user boundary is the same HTTP surface the browser uses.
- UT-15.1 through UT-15.14: human visual and audible judgement of the presented banner (WEB.md tier 3). No browser stack is added; these remain UTs. If the UT count later justifies a headless-browser harness, that is a separate, human-approved test-architecture decision.

### Infrastructure contract

No Exodan or Caddy change. SSE is ordinary HTTP over the existing reverse-proxy boundary; the app owns the new routes. Note for deployment review: confirm the reverse proxy does not buffer or time out the `text/event-stream` response (Caddy passes SSE through by default), so this is a verification point, not a contract change.

### Limitations noted for decision

- Timer configuration persists (AC15.16), but the live running state does not: a server restart mid-meeting clears any active countdown, leaving the room with its saved configuration and no active timer. Persisting a live countdown across restarts is out of scope.
- Audible delivery cannot be guaranteed for a muted or backgrounded browser tab.
