## Status

DRAFT — awaiting decisions (see "Open decisions"). No code has been written. This issue **supersedes AC13.2** introduced in #13, so the ACs and IDs below are provisional until the decisions are made.

## Problem

Two public-surface hardening changes to the moderator entry route `/<room>/moderator`, following #13. Both reduce what the public web discloses.

- **(a) Inactive rooms return 404.** Today the moderator entry form is served for any syntactically valid slug regardless of registry state. The form should be presented only when the room is active now; for any not-active room the response should be the same inactive 404 an ordinary guest receives.
- **(b) Relabel to "Login".** The entry page is headed "Moderator access" and other public copy uses the word "moderator". Relabel the page to "Login" and remove "moderator" from the public copy.

## Open decisions

1. **The two-stores coupling (a).** The moderator route has no notion of "active" of its own. The only "active" is the time registry from #7 (`rooms.csv`, populated by `meet create`). So (a) means the moderator login form appears only when the room has been created via `meet create` **and** is currently inside its window. A room present in the moderator allowlist but never created in the registry becomes unreachable through the web form. This matches the stated goal of gating access by both time slot and named moderator, but it is a real behavioural change. The CLI issuance path (`meet moderator-link --send`) is unaffected and still covers not-yet-active or unregistered rooms. Confirmation required.
2. **Delivery vehicle.** BYPASS-GATE-7 (small, clearly-scoped) versus the normal two gates. Because this supersedes an approved AC, updates roughly a dozen approved #12 test setups, and couples two subsystems, it is a moderate change rather than a one-liner. Decision required.
3. **Copy scope (b).** Heading and title only, or also the failed-link and check-email copy. Recommendation: the fuller scrub, consistent with "less on the public web". The magic-link email body is not public web and is left unchanged unless requested.

## Supersession of AC13.2

**AC13.2 today (verbatim):**

> "Given a path that is not a single-segment meeting-room slug, inactive-room messaging is absent from route-specific non-room responses; in particular the `/<room>/moderator` entry response does not vary with the room's registry state, so it cannot be used as an oracle for slug validity."

**Plain English.** Visiting any moderator page shows the same login form no matter the room's state (unknown, scheduled, finished, cancelled, live), so it cannot be used to discover which room names are real.

**Why it is too strong.** The guest gate `/X` already reveals whether X is active now (meeting page versus inactive 404). A moderator route that reflects the same active/inactive distinction leaks nothing further, provided every not-active state returns the identical 404. The blanket "must not vary with registry state" is therefore stronger than the real requirement.

**Replacement (AC14.1 below), in plain English.** Visiting `/<room>/moderator` shows the login form only when the room is live now; in every other case it returns the exact same 404 a guest gets for an inactive room. The moderator page reveals no more about a room name than the plain room URL already does, and never lets anyone tell a scheduled-but-not-yet-open room apart from a name that was never registered.

At implementation time AC13.2 is marked `🚫 Superseded by AC14.1` in `docs/ACs.md` with its text struck through and preserved; its tests RT-13.7 and RT-13.14 are marked removed there.

## Condition Coverage

AC14.1 conditions: active room serves form; unknown, before-window, after-window, cancelled each return the inactive 404; those four are mutually byte-identical; the moderator path matches the plain room path for the same not-active room; POST (form submission) to a not-active room fails closed with no delivery.

AC14.2 conditions: entry heading is "Login"; entry title is "Login"; entry body free of "moderator"; failed-verify copy free of "moderator"; check-email copy free of "moderator".

## Solution Design

### Recommended approach

- Factor an `roomActiveNow(room string) bool` helper out of `gateAllows` in `internal/server/server.go`: true when `Rooms == nil` (legacy/unconfigured), otherwise true only when the latest row is `created` and `now` is within `[valid_from, valid_until]`. Re-express `gateAllows` in terms of it to keep a single source of truth for "active".
- In `handleModerator` (`internal/server/moderator_auth.go`), after the existing `validRoomSegment` check and before the method switch, return `s.renderInactiveRoom(w)` when `!roomActiveNow(room)`. This gates both GET (the form) and POST (submission), so no magic link can be requested for a not-active room.
- Reuse the exact `renderInactiveRoom` response from #13 so the moderator not-active page is byte-identical to the guest inactive page (AC14.1, RT-14.7).
- Do **not** gate `/<room>/moderator/verify`. It is token-based, reveals no registry state, and gating it would break a legitimate click that lands just outside the window (the moderator JWT is designed to bypass the window). Left unchanged.

### (b) exact copy changes

- Entry page `Title` and `Heading`: `"Moderator access"` → `"Login"`.
- Failed-verify `Message`: `"Invalid or expired moderator link."` → `"Invalid or expired link."`.
- Check-email `Message`: `"If that address is authorised, check your email for a moderator link."` → `"If that address is authorised, check your email for a login link."`.
- Entry form `Message` (`"Enter the preapproved email address for this room."`) is unchanged; it contains no "moderator".
- The magic-link email copy (`"Your moderator link"`, `"Open this moderator link:"`) is not public web and is left unchanged pending a separate decision.

### Two-stores coupling

The moderator allowlist (`ModeratorAuth.Rooms`, from host secrets) and the time registry (`rooms.csv`, from `meet create`) are independent stores. After this change the **web self-serve** route requires both: an active registry window and an allowlisted email. The **CLI** issuance path (`CreatePrintedModeratorMagicLink` / `CreateDeliveredModeratorMagicLink`) does not pass through `handleModerator` and stays available for any room regardless of registry state, providing the fallback for early or unregistered cases.

### Early-setup trade-off

A named moderator cannot self-serve a link before `valid_from`, because the route returns 404 while the room is not active. Mitigations: set each room's `valid_from` a little before the advertised start to give moderators setup time, or issue the link via the CLI for early cases.

### Test blast radius

- `tests/regression/registry_gate_test.go`: RT-13.7 and RT-13.14 assert the superseded behaviour and are replaced by the AC14.1 tests; they are marked removed in `docs/ACs.md`. RT-13.8 and RT-13.9 (nested paths) are unaffected.
- `tests/regression/moderator_auth_test.go`: roughly a dozen #12 tests exercise `/allowed-room/moderator` and `/workshop/moderator` for rooms that are never registered. Their fixtures must register an active room before hitting the route, otherwise they will now receive the inactive 404. This updates the test setups, not the #12 ACs, whose meaning (generic responses, allowlist gating, no disclosure) still holds when the room is active.
- `tests/regression/moderator_cli_test.go`: unaffected; the CLI path does not pass through the gated handler.
- New tests: RT-14.1 through RT-14.11 in a dedicated file.

### Anti-patterns to avoid

- Do not gate the `/<room>/moderator/verify` route.
- Do not let the four not-active states differ from each other or from the guest inactive page.
- Do not change the guest gate; #13's ACs other than AC13.2 stand.
- Do not test by grepping templates; exercise the HTTP handler and assert on served responses.

### Infrastructure contract

No Exodan or Caddy change. App-side HTTP route semantics only, behind the reverse-proxy boundary, consistent with #13.
