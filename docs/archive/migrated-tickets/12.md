## Original issue body

## Problem

The existing `meet token --room <name>` flow is operator-driven and produces a short-lived all-rooms moderator URL. That remains useful for the operator, but it does not support preapproved moderators who can obtain moderator access for one specific room without receiving broad operator access.

The application needs a room-scoped moderator authentication flow. A preapproved email address should be able to visit `https://<domain>/<room>/moderator`, enter that email address, and receive a magic link only when the configured room-to-email relationship allows it. The enduring authority should live in host secrets as predefined room-to-moderator relationships, while emailed magic links and moderator JWTs remain short-lived.

The design must preserve the current room registry model: guest access remains governed by room activation windows, and reusing a room name remains possible by creating a later registry row for that same room. The existing operator ability to generate a super-moderator link for all rooms must remain available regardless of room-specific moderator definitions.

## Solution Design

### Recommended Approach

Add a room-scoped moderator magic-link flow alongside the existing operator super-moderator token flow.

The existing `meet token --room <name>` command remains the direct operator path and continues to create an all-rooms moderator JWT. The new web and CLI flows are for preapproved moderators and must not grant app-wide moderator authority.

Application-side authorization is authoritative: `moderator-auth` in host secrets decides whether an email address may obtain moderator access for a room. 8x8/JaaS does not decide the email-to-room relationship. The final JaaS JWT room claim is used as token containment and defence in depth after the application has already authorized the request. Room-scoped flows mint JaaS JWTs for one room, and the local gate verifies that room binding before allowing room-window bypass.

### Infrastructure Contract And Secrets

This design follows the current Exodan NixOS project integration contract:

- Deployment is handled by `deploy-nix`, not app-owned deploy targets.
- The app reads runtime paths from environment variables: `DEFAULT_CONFIG_PATH`, `CONFIG_PATH`, `SECRETS_PATH`, `STATE_DIRECTORY`, and `ADDR`.
- Host-specific public config remains in `config/<host>.yaml` and must not contain moderator email mappings.
- Host-specific secrets live in `secrets/<host>.yaml.age`. At runtime, `deploy-nix`/agenix decrypts that YAML and supplies its path through `SECRETS_PATH`.
- The service and the generated `meet-admin` wrapper receive the same config, secrets, and state contract. CLI moderator-link generation must use that wrapper/runtime contract rather than hardcoded host paths.
- NixOS app secrets are YAML. Do not introduce `secrets/<host>.env.age` for this feature.

Plaintext example shape only; actual host values belong in `secrets/<host>.yaml.age`:

```yaml
moderator-auth:
  enabled: true
  magic-link-ttl: 15m
  moderator-jwt-ttl: 2h
  from-email: meet@lobb.ie
  smtp:
    host: smtp.resend.com
    port: 587
    user: resend
    pass: <secret>
  rooms:
    enduring-room:
      moderators:
        - moderator@example.com
        - second@example.com
    workshop-april:
      moderators:
        - facilitator@example.com
```

Config loading should normalize moderator emails case-insensitively. Room keys should use the same single-segment room validation as `handleRoom`: non-empty and no slash.

### Existing Patterns To Follow

- Use Go and the existing single-binary `net/http` server shape.
- Keep mutable state in `STATE_DIRECTORY`, following the append-only CSV pattern used by `internal/server/roomslog.go`.
- Reuse the existing config cascade in `cmd/meet/main.go`; add typed config fields rather than ad hoc environment parsing.
- Use the existing `github.com/golang-jwt/jwt/v5` dependency for JaaS moderator JWTs.
- Borrow the `writeback` single-use pattern: random nonce, HMAC-signed magic token, token hash in durable state, consumed marker on verify.
- Borrow the `upload` external response pattern: syntactically valid web submissions always show a generic check-email page for authorised and unauthorised addresses.
- Use `html/template` for the moderator entry, check-email, and invalid-link pages, consistent with the current embedded page template.

### HTTP Flow

Route shape is room-first:

- `GET /<room>/moderator` renders an email-only moderator entry form for the path room.
- `POST /<room>/moderator` validates email syntax and path-room syntax, checks `SECRETS_PATH` moderator-auth relationships, creates a magic link only for authorised pairs, sends email through SMTP, and renders the same check-email page for all syntactically valid submissions.
- `GET /<room>/moderator/verify?token=...` verifies and consumes the magic token for the path room, then redirects to `/<room>?jwt=<room-bound-moderator-jwt>`.

The form should not accept a room field. The room authority comes from the URL path only.

Routing must recognise `/<room>/moderator` and `/<room>/moderator/verify` before the catch-all meeting-room handler. Nested rooms remain invalid; `/bad/name/moderator` must not become a moderator page.

### CLI Flow

Keep the existing operator path:

- `meet token --room <room>` continues to print a super-moderator URL whose JWT has `room: "*"` and whose lifetime is controlled by the existing `--expiry` flag.
- This path must work even when `moderator-auth` is absent from config/secrets.

Add a distinct room-scoped operator path, for example:

```bash
meet moderator-link --room <room> --email <email> [--send | --print]
```

Expected behaviour:

- Uses the same `DEFAULT_CONFIG_PATH`, `CONFIG_PATH`, `SECRETS_PATH`, and `STATE_DIRECTORY` cascade as the service and `meet-admin` wrapper.
- Validates the email-room pair against `moderator-auth.rooms` in host secrets.
- For `--send`, sends the same magic-link email as the web flow.
- For `--print`, prints the magic link for operator handoff without SMTP, but still creates durable verifier state and still produces only a room-scoped final JWT after verification.
- Rejects unauthorised email-room pairs without creating verifier-accepted token state.

The CLI path is useful for operator-assisted recovery, testing, and cases where the moderator cannot use the web form.

### Token And State Model

Add an append-only state file, e.g. `moderator_links.csv`, with rows such as:

```csv
timestamp,token_hash,email_hash,room,status,expires_at,note
```

Suggested statuses: `issued`, `delivered`, `printed`, `failed`, `used`.

Magic-token payload should include at least:

```json
{"email":"moderator@example.com","room":"enduring-room","nonce":"...","exp":1234567890}
```

Verifier acceptance rules:

- HMAC signature is valid.
- Token has not expired.
- Payload room equals the path room in `/<room>/moderator/verify`.
- Latest state for the token hash is `delivered` or `printed`.
- Token hash is not already `used`.
- The email-room pair is still authorised in the current secrets config.

After acceptance, append `used`; later verification of the same token fails.

Store token hashes only. Do not store raw magic-link tokens or moderator JWTs.

### Authorization Boundary

The application is the source of truth for moderator authorization:

- Web flow: `POST /<room>/moderator` authorizes the submitted email against `moderator-auth.rooms[<room>]` from `SECRETS_PATH` before creating any usable magic-link state.
- CLI room-scoped flow: `meet moderator-link --room <room> --email <email>` performs the same authorization check before printing or sending a magic link.
- 8x8 receives only the resulting signed JWT. It is not responsible for deciding whether the email was allowed for the room.
- The JWT `room` claim limits what an issued bearer token can do if copied or reused during its lifetime. It does not replace application-side authorization.

### Existing Moderator Mechanics Change

Current mechanics:

- `meet token --room <room>` prints `/<room>?jwt=<jwt>`.
- The JWT currently carries `room: "*"`.
- The local gate currently treats any valid moderator JWT as a bypass, without comparing the JWT room claim to the URL path.

New mechanics:

- Super-moderator CLI links keep the wildcard claim: `room: "*"`.
- Web and room-scoped CLI magic links eventually mint final moderator JWTs with `room: "<authorised-room>"`.
- The local gate changes from “valid moderator JWT exists” to “valid moderator JWT exists for this path”. The helper should receive the path room and accept only:
  - `claims.room == "*"` for super-moderator CLI links, or
  - `claims.room == pathRoom` for room-scoped moderator links.
- The gate still relies on JWT signature and time validation through `github.com/golang-jwt/jwt/v5`.

This preserves all-rooms operator power while making preapproved moderator access room-specific.

### Email Delivery

Use an interface-based mailer so regression tests can use a capture mailer and failure mailer. For production SMTP, prefer the stronger `writeback` pattern: explicit SMTP client, STARTTLS when offered, structured errors, and RFC-safe mail headers via `net/mail` where display names are needed.

Email body should contain the magic link and expiry language only. It must not contain the final moderator JWT.

Missing SMTP config or SMTP send failure must fail closed. A web submitter still sees the generic check-email page, but the verifier must not accept a token unless delivery reached a `delivered` state. For CLI `--print`, the explicit operator action can create a `printed` state without SMTP.

For real-user alignment:

- Form tests simulate a moderator loading `/<room>/moderator`, entering email, and observing either the check-email page or invalid-input response.
- Verify tests simulate the moderator opening the emailed link and observing either a redirect to the room with JWT or an invalid-link page.
- Gate tests simulate guests, room-scoped moderators, and super-moderators loading room URLs and observing whether the meeting page is served.
- CLI tests simulate the operator using `meet`/`meet-admin` style subcommands and observing stdout, stderr, exit code, captured email, and subsequent verifier behaviour.

### Anti-Patterns To Avoid

- Do not log raw magic-link tokens, moderator JWTs, or full email addresses. This follows CODING.md `Logging` and `Secrets Management`.
- Do not place moderator email mappings in committed `config/<host>.yaml`; they belong in `secrets/<host>.yaml.age` and are read through `SECRETS_PATH`.
- Do not add a database just for this feature. The existing room registry uses append-only CSV state; a second append-only log is sufficient and easier to operate.
- Do not use regex or line-oriented edits for CSV/YAML. Use `encoding/csv` and `gopkg.in/yaml.v3`, per CODING.md `Data Handling`.
- Do not build HTML, email headers, JSON, or URLs with unsafe string concatenation. Use `html/template`, `net/mail`, JSON encoding, and URL builders/query encoders where needed, per CODING.md `Cross-Language Escaping`.
- Do not suppress send, parse, signing, or append errors. Handle each explicitly, per CODING.md `Error Suppression -- Forbidden Patterns`.
- Do not write tests that grep source templates. Test rendered responses, redirects, cookies/state, captured outbound email, and CLI output, per TESTING.md `The real-user test` and WEB.md `Source vs Rendered Tier Model`.
- Do not add app-owned deploy scripts, systemd units, sudoers rules, host paths, or host package assumptions. Infrastructure ownership remains in Exodan.

### Review Notes

The design matches the current codebase shape: `cmd/meet/main.go` already wires config, room logs, JWT keys, CLI subcommands, and routes; `internal/server/server.go` already centralizes the room gate; `internal/server/roomslog.go` already establishes the append-only state pattern.

The design also matches the Exodan contract: secrets are app-owned encrypted YAML in `secrets/<host>.yaml.age`, deployed by infrastructure, and consumed via `SECRETS_PATH` by both the service and `meet-admin` wrapper. The application owns the shape and semantics of `moderator-auth`; infrastructure owns decryption, process environment, service invocation, Caddy, DNS, and host policy.
