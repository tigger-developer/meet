## Original issue body

## Problem

`meet-token` is hardcoded to the `token` subcommand of `meet`. It is the operator's only way to run a `meet` subcommand on a remote host without manually constructing the config cascade path. With #7 (`meet create / cancel / list`) and future subcommands, the gap widens: every new subcommand requires the operator to either install `meet` locally and point it at a remote state directory (it can't — state lives on the deploy host) or ssh in and remember the `--config defaults.yaml,/srv/meet/repo/config/<host>.yaml,/etc/meet/secrets.yaml` incantation by hand.

The hardcoded shim was justified when there was a single subcommand worth remoting. It isn't anymore.

## Out of scope

- Any change to the `meet` binary itself or its subcommand semantics.
- SSH multiplexing, parallelism, or background-mode connections — straight `ssh host cmd` per invocation, same as today's `meet-token`.
- A bidirectional control channel or daemon mode. This is a one-shot shim.

## Solution outline

`cmd/remote-token` is removed. A new binary `cmd/meet-helper` ships in its place:

- Invocation: `meet-helper <host> <subcommand> [args...]`.
- The shim ssh's to `<host>` and runs `/srv/meet/meet --config defaults.yaml,/srv/meet/repo/config/<host>.yaml,/etc/meet/secrets.yaml <subcommand> [args...]`, streaming stdout/stderr back.
- Help (`meet-helper -h`) explains the contract: this is a thin SSH shim; subcommand semantics are whatever the remote `meet` binary supports.
- The `meet-token` symlink at `~/.local/bin/meet-token` is replaced by `~/.local/bin/meet-helper` via the existing `make install` / `make uninstall` plumbing.

Command construction is extracted into a pure helper function so the shim's "this is the line that ends up at ssh" behaviour is unit-testable without actually opening an SSH connection.

## Notes on test classification

- RTs build the binary via `go test` exec helpers (no `make`) and run it with `--print-command` (a new internal-only flag that prints the ssh argv it would invoke instead of executing it). This lets tests verify command construction without opening real SSH connections. The print-command path is exercised exclusively in tests.
- Alternatively, the command-construction logic is extracted into a pure exported function and unit-tested directly; the choice between print-command and pure-function testing is a solution-design detail recorded in the comment below SATISFIED.
- UT-8.1 is the live-deployment check and is the only test that opens a real SSH connection.
