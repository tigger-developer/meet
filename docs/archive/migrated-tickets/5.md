## Original issue body

## Bug

Guests visiting plain meeting URLs (no JWT) on `https://meet.lobb.ie/<room>` see another user's display name prepopulated on the prejoin screen. The leak has been reported by multiple unrelated guests in different countries, ruling out local browser storage as the cause.

No code path in the repository writes any display name into the served HTML. The only `default-moderator-name` field is read solely by `cmd/meet/main.go:runToken` for moderator-JWT generation. The leak originates server-side at JaaS — almost certainly an account-side default tied to the API-key owner — and is reflected back to every visitor unless the meeting page explicitly overrides it.

## Fix

In `internal/server/static/index.html`, pass an explicit empty `userInfo.displayName` to the `JitsiMeetExternalAPI` constructor on every visit. This overrides any JaaS-side default; no operator name reaches guests through the served payload.

```javascript
const opts = {
    roomName: "{{.AppID}}/{{.RoomName}}",
    parentNode: document.querySelector('#jaas-container'),
    userInfo: { displayName: '' }    // explicit override of JaaS-side default
};
```

## Violated AC

No covering AC exists in this project yet; `docs/ACs.md` has not been introduced. The underlying behaviour ("the served meeting page does not communicate operator identity to guests") was never specified. Per the SDLC, a bug whose underlying behaviour was never specified would normally be reshaped as a feature issue with a fresh AC. This issue is retained as a bug-fix shape on operator direction; the implicit requirement codified by the fix is recorded here for traceability.

## Regression test

A single regression test exercises the runtime configuration cascade (`config/defaults.yaml` -> `config/<host>.yaml` -> `secrets/<host>.yaml`/`.age`) with a non-empty sentinel value seeded as `default-moderator-name` at the deepest layer, then asserts that the sentinel string does not appear anywhere in the body of the meeting-page response for either a no-JWT request or a JWT-bearing request. An empty resolved value would render the assertion vacuous and must be excluded by the test setup.

## Out of scope

- Lobby auto-knock, prejoin enforcement, and start-muted defaults that were bundled with this issue at an earlier drafting stage. These are feature additions, not part of the bug fix. They are also client-side `configOverwrite` directives bypassable via DevTools and therefore not a meaningful access gate. The hard gate against unscheduled or out-of-window meeting access lives in #7 (server-side time-bound room registry). A separate UX-defaults issue can be raised later if any of those behaviours are still wanted.
- Any change to the moderator JWT generation in `runToken` — the `default-moderator-name` field continues to populate the JWT's `context.user.name` claim, which is correct and intentional for moderator identification within the meeting.
