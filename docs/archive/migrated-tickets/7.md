## Original issue body

## Problem

A meeting room on the deployed instance is created implicitly the first time anyone visits its URL. `https://meet.lobb.ie/<anything>` loads a meeting page and starts a JaaS room. Two consequences follow:

- Anyone on the public internet who guesses or stumbles into a path can start a meeting in the operator's account, consuming JaaS quota and appearing under the operator's identity.
- The operator has no way to schedule a meeting in advance, control when its URL becomes live, or revoke it.

The intended behaviour, by contrast: the operator schedules meetings ahead of time, shares a stable easy-to-remember URL with participants, and that URL works only during the scheduled window. Outside the window, or for an unscheduled name, the URL is dead.

This issue introduces a server-side, Go-decided gate. The check happens before any HTML is served, so it cannot be bypassed by a visitor editing client-side JavaScript via DevTools.

## Out of scope

- Issue #6 (Cloudflare Stream recording upload).
- The pre-existing display-name leak that was the original content of this issue — promoted to its own forthcoming issue covering `userInfo.displayName=''` and any JaaS-side soft defaults (prejoin, lobby auto-knock, mute defaults). These are independent of access control; the registry is the real gate.
- Caddy or other proxy-layer changes.
- A web UI for managing the registry. CLI only for this issue.

## Solution outline

A persistent append-only registry in the state directory records the lifecycle of each meeting room. The web server consults the registry on every request before serving the meeting page. Three CLI subcommands manage the registry from the operator's terminal.

- Registry storage: `$STATE_DIRECTORY/rooms.csv`, append-only, mutex-protected, last-row-wins per room. Same pattern as `tigoss/upload/internal/handler/uploadlog.go` and the recordings log being introduced in #6.
- Columns: `timestamp` (event recorded), `room`, `status` (`created` | `cancelled`), `valid_from`, `valid_until`, `note`.
- `handleRoom`: before rendering the meeting page, look up the latest row for the requested room. A valid moderator JWT bypasses the check. Without a JWT, the room must exist, be in the `created` state, and `now` must be in `[valid_from, valid_until]`. Otherwise the response is a "no such meeting" page.
- CLI: `meet create --room <name> --from <ts> --until <ts> [--note ...]`, `meet cancel --room <name> [--note ...]`, `meet list [--filter active|upcoming|past|cancelled|all]`.
- The `default_room` config field is dropped entirely. `/` 404s like any other unregistered path, and `meet create` requires `--room` as a mandatory flag — explicit room naming, no implicit auto-creation under a default name.

Full design (storage schema, CLI flags, JWT bypass mechanics) is finalised in the `/design-solution` step after SATISFIED.

## Notes on test classification

- All RTs construct the server with `httptest` plus a controllable clock so time-window assertions are deterministic.
- RTs that involve the CLI subcommands invoke the subcommand entry points directly (not via `os/exec`), feeding stdin/stdout/stderr buffers and asserting against the resulting `rooms.csv` state.
- UT-7.1 is the sole human-verified test and is required because end-to-end "operator schedules, participant joins" is only meaningful against the live JaaS integration and a real browser.
