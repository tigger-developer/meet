## Original issue body

## Problem

Meeting video recordings cannot be uploaded to the Nextcloud WebDAV destination. The deployed meet instance on light-hugger has been retrying the 12 May `readers-2026-05-12` recording (2.4 GiB) since the session ended; every PUT to `nc.tigger.ie` returns HTTP 500 with Apache's default error page (not Nextcloud's). Two retry cycles have run to completion (the live one over ~17 hours of exponential backoff, then a second on 15 May after a service restart triggered recovery-on-startup); each has terminated at the give-up condition with the file still in `/var/lib/meet/download/`.

Infra has ruled out the obvious server-side caps on `nc.tigger.ie`: `post_max_size: 16G`, `LimitRequestBody`: unlimited, `max_input_time: -1`, `max_execution_time: 0`, 14 GiB free on `/mnt/ncdata`. PHP `memory_limit: 512M`.

The Apache default error page (rather than a Nextcloud-rendered error body) means Apache received no valid response from PHP-FPM — PHP died mid-request. The strongest hypothesis given the surviving config is Nextcloud's server-side encryption module OOMing on the large video PUT against the 512 MiB PHP memory limit. Chat JSON (small) uploaded successfully in the same process moments earlier, so credentials, reachability, and the lock at `/etc/meet/secrets.yaml` are not implicated.

Rather than diagnose and mitigate the Nextcloud-side OOM (which would couple the meet pipeline to an unrelated server's encryption configuration), the pipeline pivots: video recordings move to Cloudflare Stream, which is designed for the workload (resumable TUS upload, no body cap, adaptive-bitrate playback, native scheduled deletion). Chat and transcript JSON are small and uploading fine; they remain on the Nextcloud WebDAV path unchanged.

Cloudflare Stream is already wired through `media.lobb.ie/<stream_uid>` for playback, so consumers see a stable URL pattern with no new infrastructure on the meet side. Recordings are unlisted (bare URL plays for anyone who has it) with a configurable 90-day scheduled deletion enforced by Cloudflare.

## Out of scope

- The Nextcloud server-side encryption / `memory_limit` hypothesis is not investigated or remediated in this issue. The pivot moots it for video; chat and transcript paths remain on WebDAV and continue to work as today.
- Server-side rooms registry / time-bound allowlist (separate forthcoming issue).
- Issue #5 (lobby/prejoin/displayName) — independent.
- No app-side purge of the Cloudflare-hosted video. Cloudflare's `scheduledDeletion` field is the single source of truth for remote retention.
- No backfill of the stuck `readers-2026-05-12_2026-05-12_1934_4014s.mp4` file through the new pipeline; that file has been recovered out of band.

## Solution design

### Language and dependencies

Go (existing). Standard library preferred per `CODE/GO.md §"Standard Library Preference"`. New external dependencies kept to zero: TUS resumable upload to Cloudflare Stream is implemented as a small hand-rolled subset (POST create + PATCH chunks + optional HEAD resume) rather than pulling in `github.com/eventials/go-tus`. The TUS protocol surface used here is narrow (three HTTP verbs, four headers) and Cloudflare's implementation is well-documented; the dependency cost is not justified at this scope.

YAML configuration continues to use `gopkg.in/yaml.v3` (already in `go.mod`). Markdown notification doc is generated via `text/template` against a small inline template constant — single-language interpolation only (Go → Markdown), no Markdown embedded inside Go strings beyond a trivial template literal, so this stays inside the narrow exception to `CODING.md §"Code Structure"` ("Never embed one language as a string inside another").

### File layout

- `internal/server/recordingslog.go` (new) — CSV append/read API for `$STATE_DIRECTORY/recordings.csv`. Direct analogue of `tigoss/upload/internal/handler/uploadlog.go`: per-file mutex, header creation on first open, append-only writes, last-row-wins read, variable-column tolerance for forward compatibility.
- `internal/server/stream.go` (new) — Cloudflare Stream TUS client. Single exported type `*StreamUploader` with method `Upload(ctx, localPath, filename, ttlDays) (uid string, scheduledDeletion time.Time, err error)`. Encapsulates TUS handshake, chunk upload, and `scheduledDeletion` PATCH.
- `internal/server/notification.go` (new) — small helper that builds the Markdown notification document body and PUTs it via the existing WebDAV path. Reuses the `uploadToWebDAV` helper in `webhook.go` rather than duplicating it.
- `internal/server/webhook.go` (modified) — routing switch updated; `recording` case takes the Stream path; `transcript` and `chat` cases retain the existing WebDAV path. `uploadWithRetry` generalised behind a small `Uploader` interface so the backoff/retry/give-up loop is shared between WebDAV and Stream uploaders.
- `internal/server/server.go` (modified) — `Config` struct gains a `*StreamConfig` field alongside the existing `*WebDAVConfig`. `PurgeOldUploads` keeps its `maxAge time.Duration` parameter; `StartPurgeTicker` now reads `recording.local-retention-days` from config rather than the hardcoded `30*24*time.Hour`.
- `cmd/meet/main.go` (modified) — `appConfig.Recording` struct gains the five new fields. `loadConfig` applies the documented defaults after YAML unmarshal. Server wiring converts the `recording.*` fields into `*StreamConfig` and the purge duration before constructing the server.
- `config/defaults.yaml` (modified) — adds `recording.player-base-url`, `recording.cloudflare.stream-ttl-days`, `recording.local-retention-days` with their default values.
- `config/example-host.yaml.example`, `secrets/example-host.yaml.example` (modified) — document new fields with placeholder values. No real credentials in committed YAML.
- `README.md`, `docs/architecture.md` (modified) — config-fields table extended; architecture diagram and request-flow text updated to reflect the bifurcation of the post-download path.

### Uploader interface

```go
type Uploader interface {
    // Upload sends the local file to the backend. On success, returns a result
    // descriptor (UID, playback URL, scheduledDeletion as applicable). On failure
    // returns an error suitable for the retry loop.
    Upload(ctx context.Context, localPath, filename string) (UploadResult, error)
    Name() string // for logs
}

type UploadResult struct {
    StreamUID         string    // empty for WebDAV
    PlaybackURL       string    // empty for WebDAV
    ScheduledDeletion time.Time // zero for WebDAV
}
```

`uploadWithRetry` operates on this interface. The existing WebDAV implementation becomes `WebDAVUploader{cfg *WebDAVConfig}`. The new `StreamUploader{cfg *StreamConfig, http *http.Client}` is the Cloudflare path.

On successful `recording` upload, the post-success hook also: (a) appends the CSV row via `recordingsLog.Append(...)`, (b) builds and PUTs the Markdown notification doc via the WebDAV path. The post-success file move (`os.Rename` to `uploaded/`) is unchanged.

### Cloudflare Stream TUS exchange

The client implements only what's required:

1. **POST** to `https://api.cloudflare.com/client/v4/accounts/<account_id>/stream`
   - Headers: `Authorization: Bearer <token>`, `Tus-Resumable: 1.0.0`, `Upload-Length: <bytes>`, `Upload-Metadata: filetype dmlkZW8vbXA0,scheduledDeletion <base64-of-RFC3339>`.
   - Response: `201 Created` with `Location: <tus-upload-url>` and `stream-media-id: <uid>` (the latter is Cloudflare's UID for the resource).
2. **PATCH** the `Location` URL with sequential chunks.
   - Headers: `Authorization: Bearer <token>`, `Tus-Resumable: 1.0.0`, `Content-Type: application/offset+octet-stream`, `Upload-Offset: <bytes-uploaded-so-far>`.
   - Body: the next chunk of the file.
   - Chunk size: 50 MiB. Streaming chunked PUT body from a file `io.Reader` — no buffering of the whole file into memory.
3. **(Optional) PATCH** the video resource to set `scheduledDeletion` if it wasn't accepted in the `Upload-Metadata`. Cloudflare currently accepts it in the metadata, so this is a fallback only.

Per `CODE/GO.md §"HTTP Clients"`: use an explicit `*http.Client`. The control-plane calls (POST create, PATCH scheduledDeletion) get a `context.WithTimeout(ctx, 30*time.Second)`. The data-plane PATCH (chunk upload) gets no client-level timeout — large chunks can take minutes — but the surrounding `uploadWithRetry` loop owns the outer deadline, and the `http.Transport` is configured with `ResponseHeaderTimeout: 60s` so a hung server is detected without truncating a legitimately slow upload.

Errors are wrapped with operation context per `CODE/GO.md §"Error Handling"`: `fmt.Errorf("stream POST create %q: %w", filename, err)`.

### Notification document format

Markdown template, rendered via `text/template`:

```markdown
# {{.Room}} — {{.Date}}

- Session ID: {{.SessionID}}
- Recorded: {{.SessionTimestamp}}
- Duration: {{.Duration}}
- Playback: <{{.PlaybackURL}}>
- Scheduled deletion: {{.ScheduledDeletion}}
```

Rendered to a `[]byte`, PUT to `<recording.webdav.path>/<room>_<date>_<time>_recording.md` via the existing WebDAV PUT helper. Failure to write the notification doc does **not** fail the overall upload — the row in `recordings.csv` is the source of truth; the NC doc is a notification convenience. A warning is logged.

### Config defaults and gating

In `cmd/meet/main.go:loadConfig`, after YAML unmarshalling:

- If `recording.player-base-url` is empty → `https://media.lobb.ie/`.
- If `recording.cloudflare.stream-ttl-days` is zero → 90.
- If `recording.local-retention-days` is zero → 14.

In server wiring:

- If `recording.cloudflare.account-id` AND `recording.cloudflare.api-token` are both non-empty → construct `StreamConfig` and inject. Otherwise → no `StreamConfig`; `recording`-type webhooks log "Stream not configured, file kept in download/" and leave the file for later manual recovery (per `CODING.md §"Error Handling"` — fail loud, fail safe).
- If `recording.webdav.url` etc. are configured → construct `WebDAVConfig` as today. Independent of Stream config; chat/transcript paths work regardless.

### Anti-patterns explicitly avoided

- `CODING.md §"Prohibited Anti-Patterns"` — no string-built HTTP URLs (`http.NewRequest` with structured args); no `chmod 777`; no hardcoded credentials (all secrets from config cascade); no SSL verification disabled.
- `CODING.md §"Error Suppression — Forbidden Patterns"` — every error checked; `_ = err` not used. Notification doc write failures are explicitly logged and accepted, not silently swallowed.
- `CODE/GO.md §"HTTP Clients"` — no `http.DefaultClient`; explicit `*http.Client` with separate timeout strategies for control-plane vs data-plane.
- `CODE/GO.md §"Function Decomposition"` — new functions ≤ 50 lines, single responsibility.
- `CODE/GO.md §"Standard Library Preference"` — no new third-party dependency.

### Schema restructure (added after initial draft)

The `recording.*` block in the config cascade is nested two levels deep for grouping:

```yaml
recording:
  player-base-url: "https://media.lobb.ie/"
  local-retention-days: 14
  webdav:
    path: ...
    url: ...
    user: ...
    password: ...
  webhook-token: ...
  cloudflare:
    api-token: ...
    account-id: ...
    stream-customer-code: ...
    stream-ttl-days: 90
```

- `stream-customer-code` is loaded into the resolved config but unused by #6's TUS upload path (CF's TUS API authenticates with `account-id` in the URL and `api-token` in the `Authorization` header — no third credential). The field is retained for future use (e.g. canonical `customer-<code>.cloudflarestream.com/<uid>` player URLs if `media.lobb.ie` ever isn't the only player route).
- `default_room` is dropped from the config schema entirely. With #7's gating model, `/` 404s rather than mapping to a hardcoded room name, and `meet create` requires `--room` as a flag rather than falling back to a config default. Forces explicit room naming and prevents accidental "lobby" room creation.
- `exec_args` in `config/defaults.yaml` is preserved as-is — part of the deploy-infra contract for Ubuntu hosts (e.g. light-hugger).
- `addr` and `base_url` keep their underscore form — same deploy-infra contract reason.
- All new keys use hyphens (`stream-ttl-days`, `local-retention-days`, `player-base-url`, `api-token`, `account-id`) for consistency with the existing project convention (`default-moderator-name`, `8x8-keys.app-id`, `recording.webhook-token`).
- YAML deep-merge across cascade layers handles the nesting correctly without clobbering — `loadConfig` unmarshals each layer into the same struct, which extends nested maps additively rather than replacing them.
