## Original issue body

## Problem

Recurring schedules (#17) are defined in UTC. A group that meets at a fixed **local** time, for example "every Tuesday at 19:00 in Europe/Dublin", drifts by an hour against a UTC-anchored slot when the zone changes between standard time and daylight saving. This issue lets a recurring definition carry an IANA timezone (a Linux city code such as `Europe/Dublin`), so occurrences are computed in that zone and follow DST automatically. UTC remains the default when no zone is given.

**Depends on #17** (the recurrence engine). This layers a timezone onto the recurrence definition and the occurrence computation introduced there.

## Assumptions (confirm at PROCEED)

- The timezone is an IANA name resolved via the Go standard library (`time.LoadLocation`); an unknown name is rejected.
- DST transitions are handled entirely by the standard library. A local time that does not exist on the spring-forward day, or occurs twice on the fall-back day, resolves to a single well-defined instant per stdlib normalization rather than erroring.
- No zone means UTC, exactly as #17.
- The IANA database is embedded in the binary (`time/tzdata`) so zone resolution does not depend on host zoneinfo files, at a small binary-size cost.

## Usage examples

```
# Weekly at 19:00 Dublin local time; the UTC instant follows DST automatically
meet create --room writers --from 2026-08-11T19:00:00Z --repeat weekly \
  --tz Europe/Dublin

# First Wednesday monthly at 18:00 Dublin local time
meet create --room board --repeat monthly --ordinal 1 --weekday wed \
  --at 18:00 --tz Europe/Dublin

# No --tz keeps the definition in UTC (as #17)
meet create --room global --repeat weekly --from 2026-08-11T19:00:00Z
```

## Solution Design

### Recommended approach

Layer an optional timezone onto #17's recurrence definition. Add a `recur_tz` column holding the IANA name (empty means UTC). Occurrence computation builds the local wall-clock time in the zone with `time.Date(y, m, d, hh, mm, 0, 0, loc)`, which yields the correct UTC instant including any DST offset; the gate then compares against `now` in UTC as before. For weekly/every-N-weeks, the anchor's time-of-day and weekday are interpreted in the zone at each occurrence, so the UTC instant follows DST across the series. For monthly Nth-weekday, the Nth weekday and time-of-day are resolved in the zone.

DST edge cases are delegated to the standard library: `time.Date` normalizes a non-existent spring-forward local time forward and resolves a fall-back ambiguity to a single instant, so no hand-rolled DST arithmetic is written.

### Timezone database

Import `time/tzdata` in the server/CLI binary so the IANA database is embedded and zone resolution does not depend on the host's `/usr/share/zoneinfo`. This suits the minimal deployment sandbox at a small (~450 KB) binary-size cost. Validation uses `time.LoadLocation`.

### CLI

Add `--tz <IANA name>` to `create` (e.g. `--tz Europe/Dublin`), applied to a recurring definition alongside #17's flags. Validate with `time.LoadLocation` before writing; reject an unknown name. Absent `--tz` keeps the definition in UTC.

### Patterns to follow

- `time.LoadLocation` and `time.Date` for all zone and DST handling (GO.md "Standard Library Preference"); no manual offset tables.
- Injected clock (`Config.Now`) plus fixed test dates around known Dublin DST transitions for deterministic tests.
- Extend the registry CSV tolerantly, as in #17.

### Anti-patterns to avoid

- Do not compute DST offsets by hand or hard-code them; rely on the standard library.
- Do not assume the host has zoneinfo; embed `time/tzdata`.
- Do not treat a spring-forward/fall-back local time as an error; let stdlib normalization define the instant.
- Tests exercise the guest HTTP boundary and the CLI, not source greps (TESTING.md "The real-user test").

### Test plan and locations

- `tests/regression/recurrence_tz_test.go`: RT-18.1 through RT-18.7 (zoned occurrence computation and DST behaviour through the guest gate with the injected clock and fixed transition dates).
- `tests/regression/registry_cli_test.go`: RT-18.8, RT-18.9 (create subcommand zone validation).
- UT-18.1: human-verified end-to-end against the live deployment.

### Infrastructure contract

No Exodan or Caddy change; the embedded tzdata means no host zoneinfo dependency. App-side only.
