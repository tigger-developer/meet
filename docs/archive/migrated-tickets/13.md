## Original issue body

## Problem

The current room registry gate uses the default Go `http.NotFound` response for top-level meeting-room slugs that do not currently serve the meeting page. That default `404 page not found` text is too terse for genuine participants, and it also risks turning room access into a room-existence oracle if different inactive states are made distinguishable.

The application needs a single inactive-room page for every public, blocked top-level meeting-room slug, whether the slug is unknown, registered but outside its active window, or cancelled. The page should keep HTTP 404 semantics, but its content should explain that the room may be correct while not currently active.

This is a defence-in-depth requirement: it should not be possible to guess a meeting-room name by comparing the response for an unknown top-level slug with the response for a known but inactive top-level slug. For public room access, the only case where a single-segment meeting slug serves the meeting page is when the latest room row is active and the current time is inside that room's active window.

This applies only to meeting-room paths without a slash. Nested paths and moderator routes must keep their existing route-specific behaviour. In particular, `/room/moderator` must not show the inactive-room message.

## Condition Coverage

AC13.1 conditions: unregistered top-level slug; before-window room; after-window room; cancelled latest row; HTTP 404 retained; responses byte-for-byte identical (status, headers, and body) across all four blocked states; explanatory content present; meeting embed absent; `HEAD` and disallowed-method parity with no state-varying header; empty-segment `/` path routed to the same inactive response.

AC13.2 conditions: moderator route; nested invalid room path; nested moderator-like path; inactive copy absent from non-room responses; `/<room>/moderator` response invariant to registry state (active versus never-registered indistinguishable).

AC13.3 conditions: active guest path; inactive and cancelled guest paths; inactive copy absent from successful meeting responses; previously-valid slug indistinguishable from never-registered slug in status, headers, and body.

AC13.4 conditions: inactive-room response carries `Cache-Control: no-store`; meeting-page response carries `Cache-Control: no-store`.

## Solution Design

### Recommended Approach

Implement the inactive-room page inside the Go application server, in the existing room gate path.

The relevant code is `internal/server/server.go`: `handleRoom` normalizes the request path, handles moderator routes first, rejects paths containing `/`, then calls `gateAllows(path, r)`. Today, when `gateAllows` is false, `handleRoom` calls `http.NotFound(w, r)`. Replace that specific top-level room-gate failure response with a small server-rendered inactive-room HTML response that keeps status `404`.

The same response must be used for every blocked public single-segment room slug. The implementation must not branch to different visible responses for “never registered”, “registered but before window”, “registered but after window”, or “cancelled latest row”. Those distinctions may remain internal gate logic, but they must not become externally visible through status code, heading, explanatory copy, or meeting-page payload.

Required page content:

- H1: `Inactive`
- Paragraph: `This meeting room is not active. If you have been given this link for a meeting, it may be the case that this is the correct meeting room but the room is not active currently. Please check the meeting date and time.`

The response should use the same banner/domain styling pattern already used by the meeting page and moderator auth pages where practical. The content should be rendered server-side; no client-side JavaScript is needed for this page.

This issue does not change route-specific moderator pages such as `/room/moderator`. Existing moderator-JWT behaviour is governed by the already accepted moderator-access and room-gate ACs; changing that bypass would require a separate explicit supersession of those ACs. AC13.2 only pins the existing behaviour: the moderator entry route is already registry-blind (`validRoomSegment` checks syntax only, not the registry), so `/<room>/moderator` returns the same response whether or not the room is registered. This must remain true after the change so the moderator route cannot be probed as a slug oracle.

#### Indistinguishability, not just shared copy

The four blocked states must be indistinguishable through every observable channel, not only the visible copy:

- Render the inactive page from a single code path (one constant template and one fixed `pageData`), so the body bytes cannot drift per state.
- Set the same response headers in that single path. Do not let a per-state branch add, omit, or reorder headers. `Content-Type`, `Content-Length`, and `Cache-Control` must match across all blocked states, which is what RT-13.12's `HEAD` check guards.
- Keep timing uniform. The gate already reads and scans the whole registry file for both known and unknown slugs (`RoomsLog.LatestByRoom` calls `readAll`), so an unregistered slug and a registered-but-inactive slug cost roughly the same. Do not add a fast-path that short-circuits before the scan for unregistered slugs, as that would reintroduce a timing oracle.

#### Empty path and methods

- The empty top-level segment (`/`) reaches `gateAllows("")`, which returns false. Route that failure to the same inactive-room response rather than the terse Go 404, so `/` is not a distinguishable third response (RT-13.13).
- The inactive-room response must present identical headers under `HEAD` as under `GET`. Go's `net/http` omits the body for `HEAD` automatically; the requirement is that no header varies by blocked state (RT-13.12).

#### Cache-Control

- The inactive-room response and the meeting-page response both set `Cache-Control: no-store` (AC13.4), so a meeting page fetched during an active window cannot be replayed from browser or proxy cache after the window closes or the room is cancelled.

### Infrastructure Contract Answer

No Exodan or Caddy contract change is required for this feature.

Evidence from the current Exodan NixOS project integration contract:

- Caddy, DNS, TLS, systemd, users, groups, and host policy are infrastructure-owned.
- The app receives `ADDR`, config paths, secrets path, state directory, and process working directory from infrastructure.
- The app owns HTTP route semantics behind that reverse-proxy boundary.

Evidence from the current `meet` code:

- `internal/server/server.go` already receives all app paths through the Go `http.ServeMux` root handler.
- The app already distinguishes moderator routes, nested invalid paths, room registry failures, and successful meeting pages.
- The current undesired text is produced by app-side `http.NotFound`, not by a documented Caddy error-page rule.

Therefore this is an app-side server-rendering change. It should not be implemented in Caddy. It also cannot be implemented client-side alone because a browser only sees the default 404 body currently emitted by the server; the application must first return the desired HTML response.

### Patterns To Follow

- Use the existing Go `net/http` server and `html/template` rendering pattern.
- Keep the status code as HTTP 404 for inactive rooms.
- Keep route classification order unchanged: moderator routes first, nested path rejection next, room gate after that.
- Use semantic HTML with one H1 and a paragraph.
- Reuse existing domain/banner presentation helpers where possible, especially `parseDomain` and the classes already used in the server templates.
- Render the inactive page from a single fixed code path with fixed headers, so every blocked state emits identical bytes and identical headers.
- Set `Cache-Control: no-store` on both the inactive-room response and the meeting-page response.
- Route the empty path `/` gate failure to the inactive-room response.

### Anti-Patterns To Avoid

- Do not add Caddy configuration, deploy hooks, systemd changes, or Exodan files; those are outside the app repo boundary.
- Do not implement this as client-side JavaScript after a generic 404 body.
- Do not make nested paths look like inactive rooms.
- Do not return HTTP 200 for inactive rooms.
- Do not expose whether the slug was never registered, outside its window, or cancelled; all public room-gate failures should receive the same inactive-room page.
- Do not branch the response by blocked state through headers, `Content-Length`, or a fast-path that skips the registry scan for unregistered slugs; any of these reintroduces a content or timing oracle.
- Do not make the moderator entry route depend on registry state.
- Do not test by grepping source templates. Exercise the HTTP handler and assert on the served response.

### Test Plan And Locations

All tests are RTs because the behaviour is machine-verifiable through the same HTTP boundary a participant or moderator uses.

- `tests/regression/registry_gate_test.go`: RT-13.1 through RT-13.16.

Real-user alignment:

- RT-13.1 through RT-13.6, RT-13.12, and RT-13.13 simulate a participant opening blocked top-level room URLs (including `/` and a `HEAD` probe) and observing one indistinguishable inactive-room page instead of either the generic Go 404 or the meeting page.
- RT-13.7 through RT-13.9 and RT-13.14 simulate non-room and moderator-path requests and verify those routes do not inherit inactive-room messaging and do not vary with registry state.
- RT-13.10 and RT-13.11 simulate public successful and inactive room access and verify the only public meeting-page case is an active room window, with a previously-valid slug indistinguishable from a never-registered one.
- RT-13.15 and RT-13.16 assert `Cache-Control: no-store` on the inactive-room and meeting-page responses.

## AC hardening amendments (pre-PROCEED draft)

The ACs and solution design were tightened so the friendlier 404 cannot become a room-existence oracle. Summary of what changed and why:

- **AC13.1** now requires blocked responses to be **byte-for-byte identical in status, headers, and body** across all four blocked states, not merely to share a content contract. RT-13.5 was rewritten to assert that equality directly. Added RT-13.12 (`HEAD` and disallowed-method parity, no state-varying `Content-Length`) and RT-13.13 (the empty path `/` returns the same inactive page rather than the terse Go 404).
- **AC13.2** now pins the moderator entry route as invariant to registry state, so `/<room>/moderator` cannot be probed to confirm a slug. Added RT-13.14 comparing an active room and a never-registered room. No moderator-route code change is implied; the route is already registry-blind via `validRoomSegment`.
- **AC13.3 / RT-13.11** rewritten from an untestable "never a different response" into a concrete byte-for-byte equality between a cancelled/expired slug and a never-registered slug.
- **AC13.4** added: `Cache-Control: no-store` on both the inactive-room and meeting-page responses, so an expired or cancelled window cannot be replayed from cache.
- Solution design gained an indistinguishability section (single render path, uniform headers, uniform timing since `LatestByRoom` scans the whole file either way), plus empty-path, method, and cache-control notes, and matching anti-patterns.

Out of scope for this issue, tracked for a possible follow-up: asynchronous SMTP and rate-limiting on the moderator submit path (a timing side channel touching AC12.1), and confirmation of 8x8 moderator-JWT behaviour across sessions longer than the 2h JWT TTL.
